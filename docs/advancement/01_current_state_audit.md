## 2. 선행 조치: DOCX 표 유실 결함 (해결 완료)

### 2.1 증상

`성남시-지원프로그램` 실제 변환 결과물을 `python-docx`로 열어 검사한 결과:

| 문서 | 변환 결과 표 개수 | 유실된 내용 |
| :--- | :--- | :--- |
| AI 커뮤니티 활동지원 모집공고.docx | **0개** | 지원금액, 심사 배점표, 제출서류 목록, 추진 일정표 |
| ① AI 미디어 커뮤니티 활동지원_지원신청서.docx | **0개** | 신청서 양식 전체 (성명/연락처/활동계획/예산) |

신청서의 경우 본문 문단 **9개**만 남고 사실상 문서 전체가 소실된 상태였습니다.
반면 동일 원본의 PDF 변환은 정상이었는데, PDF는 `rhwp.export_pdf()`가 페이지를 그대로
벡터 렌더링하기 때문입니다.

### 2.2 근본 원인 (2중 결함)

**원인 ①: `rhwp.extract_text()`는 표 셀 내부를 순회하지 않음**

`HwpDualEngineParser`는 1차 엔진으로 `extract_text()`를 사용했습니다.
이 함수는 렌더링이 아닌 평문 노드 추출이라 **HWP 표(cell) 안의 텍스트를 전혀 반환하지 않습니다.**

지원신청서에 직접 실행한 실측 결과:

```
extract_text() 반환 길이: 218자   (표 바깥 안내 문구만)
```

그럼에도 코드는 `len(text.strip()) > 20` 이면 성공으로 간주하여,
더 나은 대체 경로로 넘어가지 않고 이 부실한 결과를 확정했습니다.

**원인 ②: 폴백 경로 자체가 무력**

폴백은 LibreOffice headless 변환이었으나, LibreOffice는 `.hwp` 바이너리를 열지 못합니다.

```
$ soffice --headless --convert-to docx "...지원신청서.hwp"
Error: source file could not be loaded
```

즉 1차 엔진이 부실한 결과를 내고, 2차 엔진은 애초에 동작하지 않는 구조였습니다.

### 2.3 해결 방법

`rhwp`가 제공하는 **`export_hwpx()`** 를 활용해 `.hwp`를 개방형 XML 포맷인 `.hwpx`로
정규화한 뒤, 이미 표 복원 기능을 갖춘 `HwpxParser`로 파싱하는 경로를 **1순위**로 삽입했습니다.

```
[변경 전]  .hwp ──> rhwp.extract_text() ──────────────> 평문 (표 유실)
                        │ 실패 시
                        └──> LibreOffice (.hwp 미지원, 동작 불가)

[변경 후]  .hwp ──> rhwp.export_hwpx() ──> HwpxParser ──> 마크다운 표 보존   ★신규
                        │ 실패 시
                        ├──> rhwp.extract_text()  (본문 전용 문서 대응)
                        │ 실패 시
                        └──> LibreOffice ➔ PDF ➔ PyMuPDF
```

`markdown_to_docx()`는 이미 마크다운 표(`| a | b |`)를 네이티브 Word 표로 변환하는 기능을
갖추고 있었으므로, 파서가 표를 제대로 넘겨주자 **별도 수정 없이 정상 동작**했습니다.
즉 결함은 변환기가 아니라 파서 측에 있었습니다.

**부수 결함 동시 수정** — `HwpxParser._parse_section()`이 `.//hp:p`로 전체 문단을
재귀 검색하여 **표 셀 안의 문단까지 중복 출력**하는 버그가 있었습니다.
(같은 표가 마크다운 표로 한 번, 평문으로 또 한 번 총 2회 출력)
자식➔부모 맵을 구성해 표 내부 문단을 본문 순회에서 제외하도록 수정했습니다.

### 2.4 검증 결과

| 문서 | 표 개수 (전 ➔ 후) |
| :--- | :--- |
| AI 커뮤니티 활동지원 모집공고 | 0 ➔ **5** |
| ① AI 미디어 커뮤니티 활동지원_지원신청서 | 0 ➔ **5** |

지원신청서 추출량은 **218자 ➔ 2,264자**로 증가했으며,

제출서류 목록, 사업추진 일정표가 모두 복원되었습니다.

> 신청서는 **빈 서식(양식지)** 이므로 원본에서도 대부분의 셀이 비어 있습니다.

## 2.5 후속 조치: 셀 병합 유실 (해결 완료)

### 2.5.1 증상

표는 복원됐으나 **병합 셀이 전부 풀려** 양식 서식이 무너졌습니다.
23행 × 10열 표가 21행 × 5열 균일 격자로 뭉개지고, 제목 행과 구분 행이
일반 셀처럼 표시되었습니다.

### 2.5.2 원인

`HwpxParser`가 표를 **마크다운 표로 변환한 뒤** Word로 넘기는 구조였는데,
**마크다운 표 문법은 colSpan/rowSpan을 표현할 수 없습니다.** 구조적 한계입니다.

원본 HWPX에는 병합 정보가 온전히 남아 있었습니다.

```xml
<hp:tbl rowCnt="23" colCnt="10" ...>
<hp:cellAddr colAddr="0" rowAddr="0"/>
<hp:cellSpan colSpan="10" rowSpan="1"/>   <!-- 제목 행: 10칸 병합 -->
```

실측: 셀 176개 중 **80개가 colSpan > 1**. 이 정보를 파서가 버리고 있었습니다.

### 2.5.3 해결 방법

마크다운을 우회하여 **셀 좌표·병합·열너비·배경색을 그대로 Word 표로 렌더링**하는
경로를 신설했습니다. 이는 [02번 문서](./02_knowledge_store_abstraction.md)의
`TableData` 스키마를 앞당겨 구현한 것이기도 합니다.

파서가 문서 순서를 보존한 `blocks`를 함께 내보내고, 변환기가 이를 직접 렌더링합니다.

| 추출 정보 | HWPX 출처 | Word 반영 |
| :--- | :--- | :--- |
| 셀 좌표 | `hp:cellAddr` | 표 격자 위치 |
| 병합 | `hp:cellSpan` | `cell.merge()` |
| 열 너비 | `hp:cellSz` | 고정 레이아웃 열너비 |
| 배경색 | `hp:tc/@borderFillIDRef` ➔ `hh:borderFill` | 셀 음영 + 굵게 |

**열 너비 역산** — 10열 중 4열은 병합되지 않은 셀이 없어 너비를 직접 알 수 없었습니다.
걸쳐 있는 병합 셀의 전체 너비에서 이미 아는 열을 빼는 방식으로 반복 역산합니다.

### 2.5.4 변환 트랙 재편

```
.hwp/.hwpx ──> [1] HWPX 구조 보존 (신규)  ➔ 병합·음영·열너비 보존, 텍스트 무손실
                   │ 실패 시
                   ├──> [2] rhwp PDF ➔ pdf2docx  ➔ 레이아웃 복원 (PDF 입력 기본 경로)
                   │ 실패 시
                   └──> [3] 마크다운 ➔ python-docx  ➔ 평문 폴백
```

**[2]번을 [1]번보다 뒤에 둔 이유**: pdf2docx는 시각적 재현도가 높지만
PDF에 공백 정보가 없어 손실이 발생합니다. 실측 비교 결과:

| 항목 | 원본 | pdf2docx |
| :--- | :--- | :--- |
| 띄어쓰기 | 대표자 정보 | 대표자정보 (공백 소실) |
| 활동분야 | 인문·사회·경제·문화·예술·과학·기타 | 예술까지만 (뒤 2개 누락) |
| 활동방식 | …·프로젝트(전시/출판/세미나 등) | 마지막 항목 누락 |

지식 인덱싱과 학습 데이터 생성에 쓰일 텍스트가 손상되면 안 되므로
**텍스트 무손실을 시각적 재현보다 우선**합니다.

### 2.5.5 검증 결과

생성된 `.docx`의 XML을 직접 계수하여 원본과 대조했습니다.

| 항목 | HWPX 원본 | 생성 DOCX |
| :--- | :--- | :--- |
| 셀 개수 | 176 | **176** |
| 병합 셀 | 80 | **80** (`w:gridSpan`) |
| 표 격자 | 23 × 10 | **23 × 10** |

추가로 원본 PDF와 생성 DOCX(LibreOffice 렌더링)를 이미지로 비교하여
병합 구조·음영·본문이 육안상 일치함을 확인했습니다.

## 2.7 파급 효과 (조치 필요)

이 결함은 DOCX 변환에만 국한되지 않았습니다.
`/api/upload`와 MCP `index_document`가 **동일한 `UnifiedDocumentParser`를 사용**하므로
(`src/api/server.py`, `src/mcp_server.py`), 그동안 지식 베이스에 인덱싱된 HWP 문서 역시
표 내용이 통째로 누락된 상태였습니다.

> **조치 필요**: 기존에 인덱싱한 `.hwp` 문서가 있다면 **전량 재인덱싱**해야 합니다.
> 현재는 재인덱싱을 하려면 원본 파일부터 다시 파싱해야 하는데, 이 불편함 자체가
> 02번 문서에서 다루는 KnowledgeStore가 필요한 이유이기도 합니다.

## 2.8 남은 개선 여지 (선택)

원본 PDF와 육안 비교 시 아직 남은 차이입니다. 모두 내용 손실이 아닌 **서식 차이**입니다.

- **제목/절 머리글 스타일** — rhwp의 HWPX 내보내기가 문서 제목과 "1. 신청인(팀)" 같은
  절 머리글을 표의 행으로 내보내므로, Word에서도 큰 제목이 아닌 일반 표 행으로 표시됩니다.
- **글자 서식** — 현재 굵게/가운데 정렬은 "음영이 있는 셀 = 머리 행"이라는 휴리스틱으로
  적용합니다. `hh:charProperties`를 조회하면 원본 글꼴·크기·굵기를 그대로 반영할 수 있습니다.
- **행 높이** — 원본의 `hp:cellSz/@height`를 아직 반영하지 않아 행이 다소 높습니다.
- **마크다운 표 헤더** — 마크다운 표는 첫 행을 헤더로 강제하므로 헤더 개념이 없는
  양식 문서에서는 첫 행이 헤더처럼 보입니다. (RAG 인덱싱 경로에만 영향, 변환 경로는 무관)

## 3. 잔여 격차 분석

고도화 문서 02~05에서 다룰 항목들입니다.

### 3.1 지식이 "검색용 벡터"로만 존재함

`KnowledgeIndexer.index_parsed_document()`는 청킹한 텍스트를 ChromaDB에 upsert할 뿐
(`src/rag/indexer.py`), **파싱 원본이나 표 구조를 어디에도 보존하지 않습니다.**

문제점:

- ChromaDB가 유일한 저장소이나 이는 RAG 검색 전용 포맷임
- 학습 데이터를 만들려면 벡터DB를 역으로 긁어야 하는 왜곡된 구조
- 청킹 전략을 바꾸면 **원본 파일부터 전부 재파싱**해야 함
- 문서 버전 관리, 갱신 감지(체크섬), 출처 위치 추적이 불가능

➔ **[02_knowledge_store_abstraction.md](./02_knowledge_store_abstraction.md)** 에서 해결

### 3.2 설정된 임베딩 모델이 실제로는 무시됨

`src/core/config.py`에 `EMBEDDING_MODEL: str = "BAAI/bge-m3"`이 선언되어 있으나,
`indexer.py`의 `collection.upsert()`는 문서 텍스트만 넘기므로 **ChromaDB 기본 내장 임베딩**이
사용됩니다. 즉 이 설정값은 코드 어디에서도 참조되지 않는 **죽은 설정**입니다.

이 상태에서는 학습한 임베딩 모델을 추론에 재투입하는 순환 구조를 만들 수 없습니다.

➔ **[03_embedding_provider_abstraction.md](./03_embedding_provider_abstraction.md)** 에서 해결

### 3.3 하이브리드 검색이 "재정렬"에 그침

`HybridRetriever`(`src/rag/retriever.py`)에는 BM25가 **실제로 구현되어 있습니다.**
다만 구조적 한계가 두 가지 있습니다.

**한계 ①: BM25가 독립 검색 축이 아님**

```python
results = self.collection.query(query_texts=[query], n_results=min(top_k * 2, 20))
documents = results.get("documents", [[]])[0]
...
tokenized_corpus = [doc.split() for doc in documents]   # ← 벡터 검색 결과에만 BM25 적용
```

BM25 코퍼스가 **벡터 검색이 이미 반환한 최대 20개 문서**로 한정됩니다.
따라서 벡터 검색이 놓친 문서는 BM25로도 결코 복구되지 않습니다.
전문 용어·품번·약어를 키워드로 잡아내는 것이 하이브리드 검색의 목적인데,
현 구조는 그 목적을 달성하지 못하고 **벡터 결과의 재정렬**에 머뭅니다.

**한계 ②: RRF가 아닌 가중 선형 결합**

주석은 "RRF 방식"이라고 명시하지만 실제 코드는 가중 합산입니다.

```python
final_score = (vector_score * 0.6) + (min(bm25_score / 10.0, 1.0) * 0.4)
```

BM25 점수를 `/10.0`으로 나누는 정규화는 코퍼스 크기와 질의 길이에 따라 척도가 달라져
안정적이지 않습니다. RRF는 점수 척도가 아닌 **순위**를 융합하므로 이런 문제가 없습니다.

**한계 ③: 매 질의마다 BM25 인덱스 재구축**

`BM25Okapi(tokenized_corpus)`가 `search()` 호출마다 새로 생성됩니다.

### 3.5 재사용 인터페이스가 MCP/REST 2종에 한정

현재 외부 노출 방식은 다음 두 가지입니다.

- **MCP (stdio)** — `mcp_config.json`으로 각 클라이언트에 개별 등록
- **REST API** — FastAPI

없는 것:

- **A2A(Agent-to-Agent) 프로토콜** — Agent Card(`.well-known/agent.json`), 스킬 디스커버리 없음
  (코드 전체 검색 결과 관련 구현 없음)
- **허브 레지스트리** — 여러 서버를 중앙에서 등록·조회하는 기능 없음

현 구조는 "중앙 허브를 통해 여러 프로젝트가 찾아 붙는" 방식이 아니라
**"각 클라이언트가 개별 설정으로 이 서버에 직접 연결하는"** 방식입니다.

➔ **[05_a2a_protocol_and_hub_registry.md](./05_a2a_protocol_and_hub_registry.md)** 에서 해결
