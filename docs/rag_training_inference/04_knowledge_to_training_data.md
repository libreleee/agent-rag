# 지식을 학습 데이터로 만드는 방법

지식베이스에 문서 형태로 쌓인 지식을 **어떻게 학습에 쓸 것인가**를 다룹니다.

- 문서가 학습 샘플로 바뀌는 과정
- **무엇을 학습시키고 무엇을 학습시키지 않을 것인가**
- 문서가 여러 개일 때 생기는 문제들
- 만드는 모델이 LLM이 아니라 **ML/DL일 때의 경로**

[01번 문서](./01_knowledge_training_inference_api_spec.md)가 파이프라인 전체를,
[02번](./02_technology_stack_and_interfaces.md)이 기술 선택을 다룬다면,
본 문서는 **학습 데이터 계층의 판단 기준**을 다룹니다.

---

## 1. 대전제 — 문서는 그대로 학습되지 않습니다

학습기는 "문서"를 먹지 않고 **샘플(sample)** 을 먹습니다.

```
[DB: 문서 형태]              [변환]                [학습기 입력]
KnowledgeRecord      →   DatasetBuilder    →    JSONL 샘플
 + ContentBlock           (규칙 / LLM)           한 줄 = 한 학습 예제
 + TableData
```

문서는 **원천**으로 보관하고, 학습 데이터는 **매번 새로 뽑아 쓰는 파생물**입니다.
`data/datasets/`에 저장할 것은 문서가 아니라 이 샘플들입니다.

### 1.1 학습 유형마다 필요한 형태가 다릅니다

| 학습 유형 | 필요한 샘플 형태 | 문서에서 뽑는 방법 |
| :--- | :--- | :--- |
| **임베딩 파인튜닝** | `(질문, 정답청크, 오답청크들)` | 표 행 ➔ 질문, 같은 문서 다른 블록 ➔ 오답 |
| **SFT (지시학습)** | `(system, user, assistant)` 대화 | 표·문단 ➔ QA 쌍 |
| **CPT (계속사전학습)** | 평문 텍스트 덩어리 | 문서 본문 그대로 |
| **ML/DL 분류·회귀** | `(특징 X, 레이블 y)` | 7절 참조 |

## 2. 문서 ➔ 학습 샘플 변환

### 2.1 규칙 기반 (LLM 불필요)

지식베이스에 이렇게 저장되어 있다면:

```json
{"type": "table", "table": {
  "cells": [
    {"row":0,"col":0,"text":"항목"},        {"row":0,"col":1,"text":"배점"},
    {"row":1,"col":0,"text":"주제성/타당성"}, {"row":1,"col":1,"text":"20"}
  ]}}
```

**LLM 호출 없이** 규칙만으로 샘플이 나옵니다.

```json
{"messages":[
  {"role":"user","content":"주제성/타당성의 배점은?"},
  {"role":"assistant","content":"20점입니다."}],
 "doc_id":"hwp_a91c...","block_ids":["tbl3_r1"],"generated_by":"rule:table_qa"}
```

헤더 행("항목/배점")과 데이터 행의 관계가 살아 있어야 가능합니다.
**병합 정보를 보존한 표 구조가 학습 데이터의 원료가 되는 지점**이 여기입니다.

비용 0원, 환각 0건이므로 **이것부터 만들어 파이프라인을 검증**하십시오.

### 2.2 DB에 문서 단위로 두는 이유

평문 파일 더미가 아니라 구조화된 레코드로 두는 실익입니다.

| 이유 | 없으면 생기는 일 |
| :--- | :--- |
| **문서 단위 분할** | 같은 문서 조각이 train/valid에 섞여 성능이 과대평가됨 |
| **선별 추출** | "공고문만", "2026년 이후만" 같은 조건 생성 불가 |
| **개정 시 회수** | 문서가 바뀌어도 옛 내용으로 만든 샘플이 그대로 남음 |
| **오염 회수** | 파서 결함 발견 시 영향 범위를 못 골라내 전량 폐기 |

마지막 항목은 이미 겪은 일입니다. HWP 표 유실 당시 `parser_version`이 있었다면
영향받은 문서만 골라 재생성할 수 있었습니다.
([실측 감사 2.7](../advancement/01_current_state_audit.md) 참조)

## 3. 무엇을 학습시킬 것인가 — 지식의 3계층

> **지식은 대부분 규칙·원칙·정답입니다. 그런데 그것을 그대로 외우게 하면 안 됩니다.**

| 계층 | 예시 | 어디에 둘 것인가 |
| :--- | :--- | :--- |
| **개별 사실** | 지원금 70만원, 마감 7/31 | **RAG** — 자주 바뀜 |
| **규칙·원칙** | 심사는 4항목 100점 만점, 중복지원 불가 | **RAG** — 개정됨 |
| **적용 능력** | 규칙을 사안에 대입해 결론을 내는 방식 | **학습** |

법률 AI가 좋은 비유입니다. 법조문을 암기시키지 않습니다.
**조문은 검색하고, 조문을 사안에 적용하는 논증 방식을 학습**시킵니다.

### 3.1 핵심 기법 — 근거를 함께 넣고 학습합니다

학습 샘플에 RAG로 찾아올 근거를 **미리 넣어둡니다.**

```json
{"messages": [
  {"role": "system", "content": "제시된 심사기준만 적용하여 평가하십시오."},

  {"role": "user", "content":
    "[근거]\n심사기준: 주제성/타당성 20 / 커뮤니티 역량 30 / 활동계획 40 / 시민참여 10\n\n"
    "[신청서]\n활동 주제: 어르신 대상 AI 문해 교육...\n\n"
    "[질문] 이 신청서를 심사기준에 따라 평가하십시오."},

  {"role": "assistant", "content":
    "○ 주제성/타당성 (20점 만점): 16점\n"
    "  - 지역 고령층 디지털 격차라는 공공적 문제를 다룸\n"
    "  - 다만 AI 활용의 창의성 측면은 일반적 수준\n"
    "○ 커뮤니티 역량 (30점 만점): 22점\n..."}
]}
```

**모델은 "20점"을 외우지 않습니다.** 주어진 기준이 무엇이든 그것을 대입해
논증하는 **형식과 판단 방식**을 배웁니다.

| 이점 | 설명 |
| :--- | :--- |
| **개정에 안전** | 배점이 20➔25로 바뀌어도 재학습 불필요. 근거는 런타임 주입 |
| **충돌 해소** | 모델이 사실을 외우지 않으므로 문서 간 모순이 생기지 않음 |
| **삭제 가능** | 문서를 지우면 그 지식은 즉시 사라짐 |
| **출처 표기** | 근거가 컨텍스트에 있으므로 인용 가능 |

### 3.2 학습으로 실제 좋아지는 것

사실 정확도가 아니라 **수행 품질**입니다.

| 학습되는 것 | 구체적으로 |
| :--- | :--- |
| **출력 형식** | 개조식(`○`, `-`), 심사의견서 서식, 공문 문체 |
| **논증 순서** | 근거 제시 ➔ 판단 ➔ 결론이라는 일관된 흐름 |
| **도메인 어휘** | "정량 목표", "성과확산", "이행사항"의 정확한 사용 |
| **인용 습관** | 주장마다 출처를 다는 버릇 |
| **거절 판단** | 근거에 없으면 추측하지 않고 "자료에 없음"이라 답하기 |

마지막 항목이 특히 중요합니다. 이를 위해 학습 데이터에 **일부러 근거가 부족한
샘플**을 넣고 정답을 "제시된 자료로는 확인할 수 없습니다"로 두어야 합니다.

### 3.3 규칙을 어디에 둘지 결정표

| 규칙의 성격 | 배치 |
| :--- | :--- |
| 자주 바뀜, 문서 많음 | **RAG** |
| 거의 안 바뀜, 짧음(몇 줄) | **시스템 프롬프트** |
| 거의 안 바뀜, 김 | **RAG** (프롬프트에 넣으면 매 요청 비용) |
| 조직 전체 불변 원칙 | 시스템 프롬프트 |
| 적용 방식·문체·서식 | **학습** |

"중복지원 불가"처럼 몇 년째 그대로인 규칙은 시스템 프롬프트가 낫습니다.
학습에 넣으면 바뀔 때 손쓸 방법이 없습니다.

### 3.4 규칙을 정말 학습시켜야 한다면

다음이 모두 참일 때만입니다.

- [ ] 최소 수년간 바뀌지 않았고 앞으로도 그럴 것
- [ ] 매 요청 프롬프트에 넣기엔 너무 김
- [ ] 바뀌면 재학습할 각오와 예산이 있음
- [ ] 규칙 자체보다 **그 규칙에 익숙한 말투**가 필요한 것

네 번째가 핵심입니다. 규칙을 아는 것과 규칙에 익숙한 사람처럼 말하는 것은
다릅니다. 학습이 잘하는 쪽은 후자입니다.

> **파인튜닝한 모델에서는 특정 지식을 삭제할 수 없습니다.** 재학습이 유일한 방법입니다.
> 2026년 공고 금액을 학습시키면 2027년에도 그 금액을 말합니다.

## 4. 문서가 여러 개일 때

문서가 늘어나는 순간 **충돌·편중·중복**이 한꺼번에 생깁니다.

### 4.1 선별 — 조건을 기록해 재현 가능하게

전부 넣지 않습니다. 조건 추출하고 **그 조건을 manifest에 남깁니다.**

```json
// data/datasets/공고문-qa-v3/manifest.json
{
  "filters": {"categories":["공고"], "is_template":false, "parsed_after":"2026-01-01"},
  "source_doc_ids": ["hwp_a91c...", "hwp_7f2e...", "..."],
  "doc_count": 42, "sample_count": 1180,
  "builder_version": "1.2", "parser_version": "2.1"
}
```

조건만 있으면 **같은 데이터셋을 언제든 재현**할 수 있고,
"이 샘플이 어디서 왔나"를 역추적할 수 있습니다.

### 4.2 충돌 — 가장 위험한 문제

```
2025 공고문 → "지원금은 1팀당 50만원"
2026 공고문 → "지원금은 1팀당 70만원"
```

둘 다 학습에 넣으면 **모델이 모순된 사실을 배우고**, 어느 쪽을 말할지
예측할 수 없습니다.

| 대응 | 방법 |
| :--- | :--- |
| **최선** | 사실 정보는 학습에 넣지 않고 **RAG로** 다룸 (3절) |
| 차선 | `valid_until` / 연도 메타데이터로 최신본만 선별 |
| 보조 | 질문에 시점을 넣음 — "2026년 지원금은?" |

**이것이 "사실은 RAG, 문체는 학습" 원칙의 실질적 이유입니다.**
문서가 하나일 땐 안 보이다가 여러 개가 되면 바로 터집니다.

충돌 탐지는 자동화할 수 있습니다 — 생성된 QA 중 **질문은 유사한데 답이 다른 쌍**을
찾아 검수 대상으로 올립니다.

### 4.3 편중 — 문서당 상한

표가 20개인 공고문은 샘플 300개, 짧은 안내문은 3개가 나옵니다.
그대로 두면 **한 문서가 데이터셋을 지배**합니다.

```python
@dataclass
class BuildOptions:
    max_samples_per_doc: int = 50        # 문서당 상한
    min_samples_per_doc: int = 1
    balance_by: str | None = "category"  # 카테고리별 균형
```

상한에 걸리면 무작위가 아니라 **블록 종류를 고루 섞어** 뽑습니다.
표만 300개면 표 질문만 잘하는 모델이 됩니다.

### 4.4 중복 — 보일러플레이트

행정 문서는 공통 문구가 많습니다.

```
"제작 결과물은 성남문화재단 지원사업을 통해 제작되었음을 명기하여야 합니다"
  ↑ 여러 공고문에 거의 동일하게 등장
```

그대로 두면 같은 샘플이 반복되어 **그 문장만 과적합**됩니다.

| 단계 | 방법 |
| :--- | :--- |
| 1차 | 정규화 후 완전 일치 제거 |
| 2차 | 질문 임베딩 유사도 기준 근접 중복 제거 |
| 유지 | 대표 1개 + 출처는 `block_ids`에 **다중 기록** |

### 4.5 증분 — 전량 재생성 금지

문서 1개 개정에 1,180개 샘플을 다시 만들면 비용도 크고 기존 샘플이 흔들립니다.

```
문서 개정 감지 (checksum 불일치)
   │
   ├─ by_doc.json 에서 해당 doc_id의 sample_id 조회
   ├─ 그 샘플만 삭제
   ├─ 그 문서만 재생성
   └─ manifest 갱신
```

`by_doc.json`(doc_id ➔ sample_ids 역인덱스)이 **문서별 선별 삭제를 가능하게 하는
실체**입니다. 이게 없으면 "특정 문서의 학습 데이터만 삭제"가 불가능합니다.

### 4.6 분할 시 주의

```
[잘못]  샘플 1,180개를 8:2로 무작위 분할
        → 같은 공고문 조각이 train과 valid에 동시 존재 → 성능 과대평가

[올바름] 문서 42개를 8:2로 분할 → 각 문서의 샘플이 한쪽에만
```

추가로 **카테고리 층화**를 하십시오. 공고문 40개·양식 2개인데 무작위로 나누면
valid에 양식이 하나도 안 들어갈 수 있습니다.

### 4.7 양식 문서 구분

지원신청서는 239셀 중 96셀만 채워진 **빈 양식**입니다.
구분 없이 QA를 만들면 답이 공란인 샘플이 대량 생산됩니다.

| 유형 | 판별 | 학습 용도 |
| :--- | :--- | :--- |
| 양식 | `fill_ratio` 낮음 | "신청서에 어떤 항목을 쓰는가" — **구조 지식** |
| 작성본·공고 | `fill_ratio` 높음 | "지원금은 얼마인가" — **사실 QA** |

## 5. RAG 쪽에도 같은 문제가 있습니다

다중 문서 문제는 학습만의 것이 아닙니다. 검색에서도 2025·2026 공고문이
함께 걸립니다.

| 대응 | 방법 |
| :--- | :--- |
| 메타데이터 필터 | 질의 시 연도·카테고리로 사전 필터링 |
| 최신 우선 | 동점 시 `parsed_at` 최신 우선 |
| 출처 명시 | 답변에 "2026년 공고 기준" 같은 시점 표기 |

**RAG는 답변에 출처와 시점을 붙일 수 있다는 것이 학습 대비 결정적 장점**입니다.
학습된 모델은 자기가 언제 자료로 그 말을 하는지 모릅니다.

## 6. 샘플 생성 비용

| 샘플 종류 | 생성 방법 | 비용·품질 |
| :--- | :--- | :--- |
| 표 ➔ 단순 QA | 규칙 (자동) | 0원, 환각 없음 |
| 근거 ➔ 판단·심사 | LLM + 사람 검수 | 비쌈, 품질이 성패를 가름 |

**단순 QA로 파이프라인을 먼저 검증**하고, 판단형 샘플은 소량 고품질로 시작하십시오.
판단형은 100개를 잘 만드는 것이 1,000개 저품질보다 낫습니다.

## 7. 만드는 모델이 LLM이 아닐 때 (ML / DL)

문서 제목에 `ml_dl`이 들어가지만, 지금까지는 LLM 학습만 다뤘습니다.
분류기·회귀기·랭커 같은 전통적 ML/DL 과제는 **경로가 근본적으로 다릅니다.**

```
LLM   : 지식 → (근거 + 질문 → 답변)  텍스트 샘플
ML/DL : 지식 → (특징 X, 레이블 y)    수치 벡터 + 정답값
```

### 7.1 지식베이스가 ML/DL에 주는 것

| 역할 | 지식베이스에서 뽑는 것 |
| :--- | :--- |
| **X (입력)** | 블록 텍스트, 임베딩 벡터, 표 통계(행·열 수, `fill_ratio`, 병합 비율), 파일 유형, 길이 |
| **y (레이블)** | `category`, `is_template`, `tags`, 사람 검수 결과, 채택·클릭 로그 |

`KnowledgeRecord`의 메타데이터가 그대로 레이블이 됩니다.
**문서를 구조화해 저장하는 또 하나의 실익**입니다 — 평문 더미였다면 레이블이 없습니다.

### 7.2 LLM 레이어를 두는가 — 시점에 따라 다릅니다

```
[학습 시]
지식베이스 ──> LLM (레이블러) ──> 약한 레이블 ──> 사람 검수 ──> ML 학습
                    ▲
              여기선 LLM을 씁니다

[추론 시]
입력 ──> ML/DL 모델 ──> 결과
         ▲
    LLM 없음. 빠르고 싸고 결정적
```

**학습 시엔 LLM을 도구로 쓰고, 추론 시엔 뺍니다.**

**학습 시 LLM의 역할**

| 역할 | 내용 |
| :--- | :--- |
| 약지도 레이블링 | 레이블 없는 문서 수천 건에 LLM이 1차 레이블 부여 ➔ 사람은 표본 검수만 |
| 데이터 증강 | 같은 의미의 질문 변형 생성 (검색 학습용 질의 다양화) |
| 어려운 음성 샘플 생성 | 헷갈리는 오답 후보 만들기 |

사람이 1,000건을 직접 라벨링하는 대신 LLM이 붙이고 사람은 검수만 하면
비용이 한 자릿수 줄어듭니다.

**추론 시 LLM을 빼는 이유**

| 항목 | ML/DL 단독 | LLM 포함 |
| :--- | :--- | :--- |
| 지연 | 밀리초 | 초 단위 |
| 비용 | 거의 0 | 호출당 과금 |
| 결정성 | 같은 입력 = 같은 출력 | 변동 |
| 오프라인 | 가능 | 외부 의존 |

문서 분류에 매번 LLM을 부르는 것은 낭비입니다. 분류기는 한 번 학습하면 끝입니다.

### 7.3 이 프로젝트에서 가치 있는 ML/DL 과제

| 과제 | 유형 | 학습 데이터 | ROI |
| :--- | :--- | :--- | :--- |
| **리랭커** (Cross-Encoder) | DL | (질의, 청크, 관련성) | **높음** — 검색 품질 직결 |
| **임베딩 파인튜닝** | DL | (질의, 정답청크, 오답들) | **높음** — 한국어·도메인 적응 |
| 문서 카테고리 자동 분류 | ML | 텍스트 ➔ `category` | 중간 — 인덱싱 자동화 |
| 양식/작성본 판별 | ML | 표 통계 ➔ `is_template` | 중간 — 규칙으로도 어느 정도 가능 |
| 표 헤더 행 판별 | ML | 셀 병합·서식 ➔ 헤더 여부 | 중간 — 청킹 품질 개선 |

**리랭커와 임베딩 파인튜닝이 가장 값어치가 있습니다.** 둘 다 LLM이 아니고,
추론 시 LLM이 필요 없으며, RAG 품질을 직접 끌어올립니다.

### 7.4 캐스케이드 — ML 단독으로 부족할 때

```
입력 ──> ML 분류기 ──┬─ 확신도 높음 (90%) ──> 결과 반환      ← LLM 없음
                    └─ 확신도 낮음 (10%) ──> LLM 판정       ← 여기만 LLM
```

전체 요청의 10%만 LLM을 타므로 비용·지연이 크게 줄면서 애매한 케이스 정확도는
유지됩니다. **LLM을 상시 레이어가 아니라 예외 처리로 두는 것**입니다.

## 8. 전체 구조

```
                    KnowledgeStore
                   (문서 + 블록 + 메타)
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
  [LLM 학습용]       [ML/DL 학습용]      [RAG 인덱스]
  (근거+질문→답)      (X 벡터, y 레이블)
        │                 │
        │                 │  ← 이 단계에서만 LLM을 레이블러로 사용
        ▼                 ▼
   SFT / LoRA        분류기·리랭커·임베딩
        │                 │
        └────────┬────────┘
                 ▼
            [추론 런타임]
   ML/DL      : LLM 없이 단독 서빙
   RAG 답변생성 : LLM 필요
```

## 9. 구현 순서

```
[1] 규칙 기반 표➔QA 빌더        ← LLM 없이 즉시 검증 가능, 비용 0
     ▼
[2] 출처 추적 + by_doc 역인덱스   ← 선별 삭제·증분 갱신의 전제
     ▼
[3] 품질 필터 + 문서단위 분할     ← 공란 셀 배제, 중복 제거, 누수 방지
     ├──────────────┬──────────────┐
     ▼              ▼              ▼
[4] 임베딩쌍      [5] 근거포함 SFT   [6] ML/DL 레이블셋
    (리랭커 포함)     (LLM+검수)        (메타데이터 활용)
```

**[1]을 최우선**으로 두는 이유: LLM 호출 없이 즉시 검증되고, 비용이 들지 않으며,
환각이 원천적으로 없습니다. 표만으로도 실용적인 데이터셋이 나옵니다.

## 10. 검증 기준

- [ ] 표 블록에서 LLM 호출 없이 QA 샘플이 생성된다
- [ ] 모든 샘플이 `doc_id`/`block_ids`로 원본까지 역추적된다
- [ ] **문서 하나를 삭제하면 그 문서에서 나온 샘플만 정확히 제거된다**
- [ ] 문서 하나가 개정되면 그 문서의 샘플만 재생성된다 (전량 재생성 아님)
- [ ] train/valid가 **문서 단위**로 분할되어 누수가 없다
- [ ] 한 문서가 데이터셋의 과도한 비중을 차지하지 않는다
- [ ] 보일러플레이트 문구가 반복 샘플로 남지 않는다
- [ ] 빈 양식의 공란 셀에서 무의미한 샘플이 생성되지 않는다
- [ ] 질문은 유사한데 답이 다른 샘플 쌍이 검수 대상으로 보고된다
- [ ] `manifest.json`으로 데이터셋 생성 조건이 재현된다
- [ ] 학습 프레임워크 미설치 상태에서도 데이터셋 생성이 동작한다
